# 验证记录

日期：2026-10-02。当前版本：0.3.0。真实服务器配置、项目清单、状态、备份与原始测量保留在仓库外。

## 0.3 注册与常驻同步

本轮在 Windows、Python 3.12.12、Git 2.53.0.windows.1 上验证了注册 CLI、后台控制器、持久 peer、Git 协调和 MCP。测试使用临时工作树或明确标记的独立副本。官方 MCP SDK 1.30.0 的真实 stdio 客户端测试通过，另一次真实客户端连接了运行中的配对服务，完成 8 个工具的发现、状态、冲突查询和新观察等待。

最终冻结版本的 15 个测试模块共 **198 项：192 通过、6 跳过、0 失败**。6 项跳过分别为本机缺少创建符号链接权限的 3 项，以及仅在隔离 Linux SSH CI 启用的 3 项。模块以 3 个独立进程并行运行，共 758.441 秒；测试前后的源码与测试文件 SHA256 清单一致。Windows 可见窗口与后台停止检查在本轮实际通过。

回归包含以下实质场景：

- 首次不一致时只注册，启动后返回 `baseline_missing`，两端文件、HEAD、index 均保持；不建立伪共同基线。
- 仓库内发现、子目录、linked worktree、嵌套边界、配置迁移、并发注册、Windows 大小写别名和 junction 拒绝。
- 双向修改、新文件、重命名、显式允许的删除；冲突阻止整批，暂停保留两端改动，过期 revision 无法解决新冲突。
- 未知写入回执不重放；重连先观察实际字节，保留断线后出现的独立编辑。
- Windows 原生文件事件、Linux inotify、定期重扫；关闭 watcher 后修改同长度内容并恢复 mtime，观察屏障仍发现变化。
- staged、intent-to-add、Git 操作与分叉阻止自动跟进；原生 index/ref 事务、失败后的锁与 journal 保留。
- 在创建 Git bundle 前审核全部待传历史；包括中途提交秘密后又删除的反例，目标端不收到该秘密对象。
- 同一配对的控制器互斥、共享远端 writer lease、只读缓存在慢检查期间可用、过期状态不显示为 `synced`。
- loopback HTTP 的 Host/Origin/实例检查、客户端拒绝重定向与非本机 URL、MCP stdout 保持协议输出。

## 0.3 真实 Windows ↔ Linux SSH

网络恢复后，在专用隔离 fixture 完成了 8 个记录步骤：初始观察屏障、缓存查询、自动推送本地编辑、自动拉回远端编辑、暂停/冲突/过期选择拒绝/显式解决、创建/重命名/删除、跟进远端原生 commit，以及 checkpoint 与两端相同 tag。最终两端 HEAD、分支与所选文件一致。

另一次测试只终止这份 fixture 控制器拥有的 SSH 客户端进程，并在断开期间保存文件。服务记录了 `offline → pending → syncing → synced`，重新连接后两端保留该编辑，整个检查约 9.1 秒。这是受控进程断连，不能代替物理断网、掉电和磁盘故障实验。

已有研究项目的独立开发配对也已迁移注册并启动。新一轮只读屏障确认双方 235 个受支持文件一致，原有共同未提交工作保留。旧项目、训练环境、数据、权重与作业没有被接管。

## 0.3 测量：查询与完成同步分别计时

以下是同一 Windows 主机在回归并行运行时的测量，属于小型验收样本，不是吞吐量承诺。SSH fixture 有 3 个初始文件；本地双目录 fixture 有 5 个。

| 操作 | 本地双目录 | 真实 Windows/Linux SSH |
|---|---:|---:|
| 缓存 API 查询，40 次中位数 | 78.79 ms | 90.74 ms |
| 缓存 API 查询，P95 | 94.90 ms | 132.85 ms |
| 缓存 API 查询，最大值 | 118.44 ms | 145.03 ms |
| 本地编辑至确认两端一致 | 2.651 s | 3.261 s |
| 远端编辑至确认两端一致 | 4.352 s | 7.096 s |
| 新文件至确认两端一致 | 4.725 s | 5.269 s |
| 远端原生 commit 跟进整段检查 | 35.885 s | 52.310 s |
| 编辑后 checkpoint/tag 整段检查 | 76.130 s | 86.410 s |

完整命令 `python -m worktree_bridge status --short` 另外测了 10 次，中位 1.471 秒、最大 1.588 秒，包含启动 Python 和命令输出；不能把 API 的毫秒数当成每次启动 CLI 的耗时。`watch` 和 MCP 复用常驻进程。Git 历史审核、bundle 与多次核验仍可能需要几十秒，但状态查询不用等待这些动作完成。

独立持久 peer 测试使用 235 个、每个 8 KiB 的文件：warm snapshot 中位 116.58 ms、最大 158.33 ms；完整内容屏障中位 740.41 ms、最大 944.44 ms。这是本地 peer 测量，不代表跨公网传输耗时。

实际 235 文件研究项目的 SSH 配对另测了 40 次缓存 API 查询：中位 92.69 ms、P95 109.66 ms、最大 115.01 ms；测量前的新观察屏障确认两端一致。真实 SSH peer 返回的文件监测后端是 Linux `inotify`。

## 自动验证与范围

运行 `python -m unittest discover -s tests -v` 使用隔离临时仓库，默认不联网。GitHub Actions 配置覆盖 Ubuntu/Windows 和 Python 3.10/3.12，并有独立 Linux loopback SSH job：自行生成一次性 client/host key、从本次 host 公钥建立信任、仅监听 `127.0.0.1`，验证真实 SSH、inotify、冲突和重连。是否通过应以对应提交的 Actions 结果为准。

Windows 缺少符号链接权限时，相应用例会明确跳过；真正的 junction 测试另行执行。未启用 CI 专用 SSH 环境时，3 个 live 用例跳过。Windows 后台启动使用无窗口解释器，并另有启动/停止及窗口回归检查。

没有验证任意网络拓扑、机器掉电、磁盘满、ACL/所有权、Unix 执行位或任意第三方编辑器的并发写入。单文件原子替换不是跨主机事务，`synced` 只代表最新有效观察。操作回执、当前状态和源文件审阅仍然必要。

## 0.2 历史记录

以下保留 0.2.0 当时的验证；它描述显式 `baseline/plan/apply` 路径，不替代上面的 0.3 常驻同步验收。

## 本地回归

环境：Windows，本地 Python 3.12.12，Git 2.53.0.windows.1。

```console
python -m unittest discover -s tests -v
```

最终集成回归52项：50项通过，2项跳过，总耗时613.825秒。按原同步核心23项、端点边界10项、SSH配置4项、验收脚本保护15项组织。两项真实Windows符号链接创建测试因当前权限不足跳过；不能将跳过计为通过。Linux上的真实祖先链接测试另已完成。

覆盖内容：

- 本地修改推送、远端新文件拉回、目标旧内容备份与成功日志。
- 两端不同修改时拒绝整批写入；计划生成后内容变化时拒绝旧计划。
- 删除和双端同删阻止；初次建基线、刷新基线不能绕过删除限制。
- 两端分支差异、旧基线 HEAD、未合并索引、未完成 Git 操作阻止。
- 基线绑定明确端点，拒绝复用到另一对目录或互相包含的本地根。
- 目标端忽略路径阻止；直接读取/写入不在 Git 选择范围中的路径被拒绝。
- 状态包含文档指纹、差异和排除理由；扫描读取错误会失败，而不是当作已忽略文件。
- 路径逃逸、`.git`、Windows 保留路径与大小写碰撞检查。
- 部分执行失败保留旧基线、备份和 journal。
- `datasets/` 中已跟踪的源码保持可见，避免误把 loader 代码当作数据排除。
- Git 定位/索引环境变量不能把另一仓库索引注入当前扫描；真实全局忽略规则仍生效。
- 根目录祖先链接与 reparse 属性检查；Git返回0但明确无法读取目录时停止扫描。
- SSH alias端口不被默认22覆盖；有效hostname/user/port变化会改变端点身份。
- 验收脚本拒绝普通项目、错误marker/哈希、复用状态、项目内报告等输入，默认测试不联网。

远端探针另以 Python 3.9 的语法版本做了解析检查。

## 独立反例复测

另一名审阅者用独立临时 Git 工作树复现并验证修复：

1. 两端已更新到同一个新提交，本地随后改回旧基线内容；计划以 `baseline_head_changed` 拒绝，原改动保留。
2. 目标端通过 `.git/info/exclude` 忽略新文件的目录；计划在写入前阻止，文件没有被创建。
3. 已存在 MERGE_HEAD 或未合并索引；计划阻止，没有把中间状态当成普通源码同步。
4. 两端都删除原有已跟踪文件；初次 baseline 和 refresh 均被拒绝，没有静默建立不完整基线。

Skill 也用“首次已有两端差异”与“同步 AGENTS.md 后继续开发”两个情景审查：保留分叉、不给旧授权升级、同步后重读规则。

0.2由指定的6.1 Sol子智能体补充端点审查和验收脚本，主智能体执行真实SSH及整合。已复现并修复：`GIT_INDEX_FILE`污染、祖先链接、权限拒绝被Git警告掩盖，以及SSH别名端口覆盖。

## 真实 SSH 只读检查

以已有 Windows 本地研究项目和 Linux SSH 对应工作树运行 `status`，服务器 Python 3.9.23。检查成功：两端各识别 146 个受支持文件，5 个大文件或压缩资产单独列出排除原因；双方 HEAD/分支可正确读取，文档指纹和文件差异可返回。

对两端 Git index 和一份有本地自定义改动的页面计算执行前后指纹，均未变化。这个原目录只读样本没有运行 baseline/apply、上传探针文件或修改训练作业；后续写入验收使用下面的独立目录。

该仓库两端有 CRLF/LF 差异，因此原型的逐字节差异列表比按 LF 归一化的人工审计更多。这是比较口径的区别，原型没有自动重写换行，也没有把状态读取成功当作允许同步。

## 真实 SSH 写入与恢复

专用隔离fixture在Windows本地和Linux服务器具有相同Git提交与明确标记。验收脚本的7个记录步骤全部成功：preflight、baseline、本地AGENTS推送、远端CONTEXT拉回、冲突plan/apply拒绝、过期计划拒绝、恢复同步。

另在真实SSH写入成功后，从客户端故意丢弃一次成功回执：旧基线保留，journal标记中断；读回实际内容后，新计划只写入剩余1个文件，最终两端一致。这是受控模拟客户端丢失回执，不是物理网络断开、进程崩溃或主机掉电实验。

Linux端专门创建并恢复了不可读的未跟踪测试子目录，确认Git会给warning且返回0；修正后的探针拒绝这次不完整扫描。祖先目录包含符号链接的路径同样被拒绝。

## 实际项目的独立副本接入

从一个实际研究项目的相同Git提交，分别创建两端独立开发副本；仅给新副本设定LF，建立新基线。通过正式计划迁入本地已有的.gitignore修改、8份部署文件和新的CONTEXT，共10项。最终两端235个受支持文件逐字节一致。

原本地与远端仓库的受支持文件、Git状态以及index/config指纹前后相同。没有复制虚拟环境、运行库、数据和权重，也没有启动训练。结果表示新开发副本已接入；旧目录不自动同步，运行环境不自动转移。

## 打包与技能

CLI 可通过仓库内入口 `python scripts/bridge.py --help` 调用，也可通过 pyproject 构建 wheel。Skill 已通过 skill-creator 的 frontmatter 校验，并有独立行为审查。0.2同时保存本地Git版本、测试脚本与私有执行回执；公开源码不包含真实端点配置。校验不证明Skill在所有Agent宿主上都能自动加载。

## 未验证与不承诺范围

- 真实SSH测试覆盖一条既有Windows↔Linux线路；没有证明所有SSH服务器、网络拓扑和中断方式都可靠。
- Windows真实符号链接创建用例跳过；Linux祖先链接已验证，完整junction/ACL/文件模式/Unicode路径矩阵仍未验证。
- 不保证任意编辑器、Git 进程或训练进程同时写入时无竞争。应用计划时要求暂停其他写入者，一个配对只用一个控制器。
- 0.2 当时没有自动监听、自动重连守护服务、自动 Git 历史协调或 MCP；0.3 的这些能力按上面的独立结果验收。
- 单文件原子替换不构成多文件/多主机事务；连接中断后必须读取实际状态，不可盲目重放。
- 当前测试不代表对全部公开竞品做过实机评测，也不构成生产级数据安全保证。
