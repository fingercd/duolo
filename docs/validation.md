# 验证记录

日期：2026-10-02。版本：0.2.0。此文件只保存通用验证结论；真实服务器配置、项目清单与内容指纹保留在仓库外。

## 本地回归

环境：Windows，本地 Python 3.12.12，Git 2.53.0.windows.1。

```console
python -m unittest discover -s tests -v
```

最终集成回归52项：50项通过，2项跳过，总耗时613.825秒。按原同步核心23项、端点边界10项、SSH配置4项、验收脚本保护15项组织。两项真实Windows符号链接创建测试因当前权限不足跳过；不能将跳过计为通过。Linux上的真实祖先链接测试另已完成。

覆盖内容：

- 本地修改推送、远端新文件拉回、目标旧内容备份与成功日志。
- 两端不同修改时拒绝整批写入；计划生成后内容变化时拒绝旧计划。
- 删除和双端同删阻止；初次建基线、刷新基线不能绕过删除限制。
- 两端分支差异、旧基线 HEAD、未合并索引、未完成 Git 操作阻止。
- 基线绑定明确端点，拒绝复用到另一对目录或互相包含的本地根。
- 目标端忽略路径阻止；直接读取/写入不在 Git 选择范围中的路径被拒绝。
- 状态包含文档指纹、差异和排除理由；扫描读取错误会失败，而不是当作已忽略文件。
- 路径逃逸、`.git`、Windows 保留路径与大小写碰撞检查。
- 部分执行失败保留旧基线、备份和 journal。
- `datasets/` 中已跟踪的源码保持可见，避免误把 loader 代码当作数据排除。
- Git 定位/索引环境变量不能把另一仓库索引注入当前扫描；真实全局忽略规则仍生效。
- 根目录祖先链接与 reparse 属性检查；Git返回0但明确无法读取目录时停止扫描。
- SSH alias端口不被默认22覆盖；有效hostname/user/port变化会改变端点身份。
- 验收脚本拒绝普通项目、错误marker/哈希、复用状态、项目内报告等输入，默认测试不联网。

远端探针另以 Python 3.9 的语法版本做了解析检查。

## 独立反例复测

另一名审阅者用独立临时 Git 工作树复现并验证修复：

1. 两端已更新到同一个新提交，本地随后改回旧基线内容；计划以 `baseline_head_changed` 拒绝，原改动保留。
2. 目标端通过 `.git/info/exclude` 忽略新文件的目录；计划在写入前阻止，文件没有被创建。
3. 已存在 MERGE_HEAD 或未合并索引；计划阻止，没有把中间状态当成普通源码同步。
4. 两端都删除原有已跟踪文件；初次 baseline 和 refresh 均被拒绝，没有静默建立不完整基线。

Skill 也用“首次已有两端差异”与“同步 AGENTS.md 后继续开发”两个情景审查：保留分叉、不给旧授权升级、同步后重读规则。

0.2由指定的6.1 Sol子智能体补充端点审查和验收脚本，主智能体执行真实SSH及整合。已复现并修复：`GIT_INDEX_FILE`污染、祖先链接、权限拒绝被Git警告掩盖，以及SSH别名端口覆盖。

## 真实 SSH 只读检查

以已有 Windows 本地研究项目和 Linux SSH 对应工作树运行 `status`，服务器 Python 3.9.23。检查成功：两端各识别 146 个受支持文件，5 个大文件或压缩资产单独列出排除原因；双方 HEAD/分支可正确读取，文档指纹和文件差异可返回。

对两端 Git index 和一份有本地自定义改动的页面计算执行前后指纹，均未变化。这个原目录只读样本没有运行 baseline/apply、上传探针文件或修改训练作业；后续写入验收使用下面的独立目录。

该仓库两端有 CRLF/LF 差异，因此原型的逐字节差异列表比按 LF 归一化的人工审计更多。这是比较口径的区别，原型没有自动重写换行，也没有把状态读取成功当作允许同步。

## 真实 SSH 写入与恢复

专用隔离fixture在Windows本地和Linux服务器具有相同Git提交与明确标记。验收脚本的7个记录步骤全部成功：preflight、baseline、本地AGENTS推送、远端CONTEXT拉回、冲突plan/apply拒绝、过期计划拒绝、恢复同步。

另在真实SSH写入成功后，从客户端故意丢弃一次成功回执：旧基线保留，journal标记中断；读回实际内容后，新计划只写入剩余1个文件，最终两端一致。这是受控模拟客户端丢失回执，不是物理网络断开、进程崩溃或主机掉电实验。

Linux端专门创建并恢复了不可读的未跟踪测试子目录，确认Git会给warning且返回0；修正后的探针拒绝这次不完整扫描。祖先目录包含符号链接的路径同样被拒绝。

## 实际项目的独立副本接入

从一个实际研究项目的相同Git提交，分别创建两端独立开发副本；仅给新副本设定LF，建立新基线。通过正式计划迁入本地已有的.gitignore修改、8份部署文件和新的CONTEXT，共10项。最终两端235个受支持文件逐字节一致。

原本地与远端仓库的受支持文件、Git状态以及index/config指纹前后相同。没有复制虚拟环境、运行库、数据和权重，也没有启动训练。结果表示新开发副本已接入；旧目录不自动同步，运行环境不自动转移。

## 打包与技能

CLI 可通过仓库内入口 `python scripts/bridge.py --help` 调用，也可通过 pyproject 构建 wheel。Skill 已通过 skill-creator 的 frontmatter 校验，并有独立行为审查。0.2同时保存本地Git版本、测试脚本与私有执行回执；公开源码不包含真实端点配置。校验不证明Skill在所有Agent宿主上都能自动加载。

## 未验证与不承诺范围

- 真实SSH测试覆盖一条既有Windows↔Linux线路；没有证明所有SSH服务器、网络拓扑和中断方式都可靠。
- Windows真实符号链接创建用例跳过；Linux祖先链接已验证，完整junction/ACL/文件模式/Unicode路径矩阵仍未验证。
- 不保证任意编辑器、Git 进程或训练进程同时写入时无竞争。应用计划时要求暂停其他写入者，一个配对只用一个控制器。
- 没有自动监听、自动重连守护服务、自动 Git 历史协调或 MCP 服务。
- 单文件原子替换不构成多文件/多主机事务；连接中断后必须读取实际状态，不可盲目重放。
- 当前测试不代表对全部公开竞品做过实机评测，也不构成生产级数据安全保证。
