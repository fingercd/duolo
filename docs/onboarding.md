# 已有项目首次接入

首次接入不能从“让 baseline 通过”倒推覆盖哪一端。先记录双方 Git SHA/分支、未提交状态、关键文档、换行与机器专用目录；保留旧工作再决定新开发位置。

## 独立开发副本路径

本项目已在一对 Windows/Linux 研究仓库上执行以下流程：

1. 两端原仓库在同一个提交。保留原工作树和 Git index/config 指纹，另行保存选定未提交文件的内容指纹。
2. 在两边新目录分别 clone 同一个 Git 版本。只为新副本设置 `core.autocrlf=false`、`core.eol=lf`；不对原目录批量重写换行。
3. 新副本使用私有、独立的 state_dir，完整 status 确认 Git 与所有受支持文件逐字节相同后建立 baseline。
4. 将经过选择的原本地未提交文件复制到新本地副本，保留原始字节及一份私有备份。通过正式 plan/apply 传到新远端副本，不直接向已有远端项目覆盖文件。
5. 共同 CONTEXT.md 记录新配对、原目录角色、同步方式、环境是否就绪及哪些改动尚未迁入。成功后重新读取，再做依赖这些信息的任务。
6. 复核原目录的受支持文件、Git状态及 index/config 指纹没有变化，保存接入回执。

这条路径的结果是“新开发副本已配对”。旧目录的后续编辑不会自动进入新配对。用户需要明确后续在哪一对目录开发，不能同时把旧目录、新目录和运行快照都当权威。

## 机器专用工作与运行环境

部署脚本和环境说明可以迁入，但内容中记录的原环境绝对路径仍属于历史事实。不要把复制脚本解释成复制了可用运行环境；虚拟环境、自定义动态库、数据和权重需按项目约定另行处理。当前工具也不传播新文件的Unix执行位。

带入 AGENTS.md 时保留项目原本的约束。同步试点没有自动获得启动训练、使用GPU、部署到机器人或发布模型的权限。已有训练继续使用原来的固定版本与环境。

## 两端已经分叉时

如果原仓库 HEAD/branch 不同，先保留双方工作并明确后续目标。新副本可以从双方认可的共同版本出发，但不能因此把其中一边的现有改动视为可以丢弃。需要逐项审阅补丁和文档；遇到同文件不同内容时，依旧遵循冲突停下的政策。

目前没有自动迁移任意历史分叉、自动合并文档或移动已运行实验的功能。MCP、后台监听和 Git 历史协调仍需分别实现与验收。
